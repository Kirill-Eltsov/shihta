# I4-A-03. Метрики, лимиты и повторы

Статус: параметры зафиксированы для передачи в реализацию до основной серии. Внешнее согласование и исполнение серии не заявляются. До начала основной серии участникам нужно подтвердить одну версию протокола; изменение после просмотра результатов оформляется отдельной серией.

## Метрики

Принимается только полный план, прошедший независимый валидатор. Objective независимо считается как sum demand*q. Для invalid_plan цель для сравнения — null; заявленная методом сырая цель сохраняется отдельно. Отсутствие плана не превращается в нулевую цель.

Для максимизации F — цель допустимого плана (нижняя граница), U — доказанная верхняя граница решателя для той же задачи. Абсолютный gap=U-F; относительный gap=(U-F)/max(abs(F),1e-9). Численные отрицательные расхождения до допуска можно обнулить, большие означают ошибку. Если F или U отсутствует, gap=null. При минимизации -F в scipy преобразовать U=-mip_dual_bound. Сырой solver gap сохраняется отдельно: его формула может отличаться. Эвристика не получает bound по умолчанию; сравнивать её с оптимумом можно лишь после доказанного решения эталона на том же входе.

## Время и повторы

Общий бюджет — 120 секунд на метод и экземпляр, включая загрузку/подготовку, прогноз или эвристику, построение модели, решение и валидацию. Каждая стадия измеряется монотонным таймером отдельно; их сумма — total_time. Solver получает оставшийся бюджет. Жёсткий общий лимит обеспечивает внешний процесс с таймаутом; это требование к runner, а не уже реализованный механизм. Превышение лимита не выдаётся за успешный запуск.

Детерминированный метод: один основной запуск и три дополнительных для времени, без выбора лучшего ответа по повторам. Отчёт времени — медиана и диапазон четырёх запусков. Стохастический метод, если используется: seeds 0–9, все результаты сохраняются. Для детерминированной жадной эвристики случайные seeds не нужны. Один поток — при поддержке; неподдерживаемую настройку отмечать. Сохранять CPU/ОС, версии и нагрузку окружения.

## Статусы

optimal — доказан оптимум и план прошёл проверку; feasible — проверенный план без доказанного оптимума; infeasible — доказана несовместность; timeout_with_plan и timeout_without_plan — разные исходы; no_solution_found — метод не нашёл решения без доказательства несовместности; invalid_plan — выход нарушает ограничения; error — ошибка программы или формата. Одновременно хранить raw_solver_status, termination_reason и validation_status, чтобы не терять ошибочный план при timeout.

## Сопоставимость и журнал

Для одного сравнения одинаковы hash сценария, q, ограничения, ресурсы и версии входов. Допуск ресурса 1e-8+1e-9*abs(stock); цель abs_tol=1e-8, rel_tol=1e-9. Изменение q создаёт другую задачу. Сохранять все отказы и логи, seed, commit, параметры, план, F, U, gap, этапы времени, отклонения бюджета и результат валидации.

Сводка: доля допустимых планов, цель допустимых, bound/gap при наличии, total_time и время первого допустимого при доступной инструментализации. Не исключать неудачные запуски из знаменателя. Текущие три малых случая — контроль корректности; будущий benchmark и G3 требуют результатов реализации Кирилла.
